# CTO-Level Codebase Audit — 2026-06-29

## Executive Summary

This repository is **not a verified 10/10 production codebase**. It is a functional, modular React/TypeScript Canvas game with meaningful refactors, CI, tests, Firebase integration, and strong player-facing scope. The uncomfortable truth is that several prior documents overstate readiness: coverage enforcement currently fails, server-side save validation is not actually a pre-write control, leaderboard writes are client-trusted, and multiple production-facing stubs remain.

**Overall score after this remediation pass: 7.2 / 10.** The codebase is shippable as a portfolio/demo game, but it is **not** ready for high-stakes monetized/competitive production without emulator-proven security rules/functions, coverage recovery, real linting, and architecture work.

## Evidence Collected

- `npm run lint` passed TypeScript validation.
- `npm test` passed 452/452 tests after adding callable-path coverage for `FirebaseService`.
- `npm test -- --coverage` passed tests but failed configured global coverage thresholds: lines 60.28% vs 80%, functions 56.62% vs 75%, branches 46.48% vs 70%, statements 59.64% vs 80%.
- `npm run build` completed, but emitted bundling warnings: circular chunk `vendor -> react -> vendor`, `DailyChallengeManager` dynamically imported but also statically imported, large Firebase/vendor chunks.
- `npm audit --omit=dev` could not complete because the registry returned HTTP 403 in this environment.
- Required searches for `SALT`, `Supabase`, and `firebase-applet-config` found no hardcoded client salt and no active Supabase usage, but did find stale/conflicting documentation and Firebase config references.

## High-Priority Issues

1. **Firestore save/leaderboard trust boundary was partially remediated in this pass.** Direct client writes to `private/saves` and `leaderboard/{userId}` are now denied, and callable functions perform authenticated Admin SDK writes. Remaining work: emulator tests, schema validation depth, rate limiting, and telemetry-backed anti-cheat.
2. **Client/server checksum design now separates local tamper-evidence from server authority.** The callable computes server and client checksums; remaining work is emulator/function tests and migration/backfill handling for old cloud save documents.
3. **Leaderboard is no longer directly client-writable, but anti-cheat is still basic.** The callable has hard plausibility bounds and monotonic preservation, but a true competitive leaderboard still needs signed session summaries, rate limits, and replay protection.
4. **Coverage gate is fictional in practice.** Configured coverage thresholds fail on the current codebase despite documentation claiming full coverage enforcement.
5. **Production stubs remain.** Monetization is a localStorage/demo stub, analytics has console/no-op style providers, ads are simulated, and some docs still frame these as complete.
6. **Architecture still contains god-class and static-manager debt.** Refactors improved the engine, but `GameEngine` remains too broad and static managers make testing and future scaling harder.
7. **Build health has unresolved warnings.** Circular manual chunks and duplicated dynamic/static imports undercut the claimed bundle work.
8. **Audit documentation has been partially corrected.** `AGENTS.md`, `README.md`, `DEPLOYMENT.md`, and this audit now reflect the current posture; older historical audit/victory-lap docs still need archival or superseded banners.

## Best Possible Plan to Reach 10/10

### Phase 0 — Truth and Release Governance (0.5 day)
- Replace all false 10/10 claims with current audited ratings.
- Add release-blocking issue labels for security, coverage, and production stubs.
- Require `npm run ci` and coverage in branch protection.

### Phase 1 — Security Boundary Repair (1–2 days)
- Move cloud save writes behind a callable HTTPS function or server endpoint that authenticates the user, validates schema, computes checksum server-side, and writes with Admin SDK.
- Change Firestore rules so clients cannot write `users/{userId}/private/saves` directly.
- Move leaderboard writes behind a server function with score sanity checks, replay/rate limits, and signed session summaries.
- Add emulator tests for Firestore rules and Cloud Functions.

### Phase 2 — Coverage Recovery (1–2 days)
- Add tests for SoundManager fallback/non-audio paths, PCGSystem generation/update boundaries, IndexedDBSaveSystem fallback paths, FirebaseService error paths, and GameEngine kill/damage/resource edge cases.
- Keep global coverage thresholds honest; do not lower them to pass.
- Add coverage summary upload in CI.

### Phase 3 — Architecture Hardening (2–4 days)
- Extract combat/kill/resource logic from `GameEngine` into a `CombatSystem`.
- Extract bug AI/movement/abilities into `BugBehaviorSystem`.
- Replace static `ProgressionManager`/`StatsManager` calls in engine paths with injected interfaces.
- Remove the legacy `__gameEngineStatus` bridge after consumers are migrated.

### Phase 4 — Production Stubs and Business Readiness (2–5 days)
- Replace monetization stub with real provider integration or explicitly exclude paid features from release scope.
- Replace analytics stub with a privacy-reviewed provider and event taxonomy.
- Add consent/privacy documentation for telemetry.
- Add product acceptance criteria for daily challenges, leaderboards, saves, and accessibility.

### Phase 5 — Performance and Operational Evidence (1–2 days)
- Fix manual chunk warnings and isolate Firebase/auth chunks from initial gameplay path.
- Add Lighthouse/Playwright smoke checks for load, PWA, accessibility, and core flow.
- Add frame-time benchmark harness for representative desktop/mobile DPR settings.
- Wire production monitoring and error reporting with documented rollback procedures.

## LARP / Self-Reflection

Assumptions I made:
- Firebase `onWrite` semantics are post-write triggers and cannot be treated as pre-write validation.
- A competitive leaderboard is a trust boundary and cannot accept raw client scores.
- Stubs are acceptable only if explicitly out of production scope.

Evidence that works:
- TypeScript compiles.
- Unit tests pass without coverage.
- Production build completes.

Evidence that it is not 10/10:
- Coverage thresholds fail.
- Security controls rely on client-authoritative writes for saves/leaderboards.
- Multiple docs claim readiness that the tooling does not prove.

## Immediate Blockers for a True Production Release

- Block direct client writes to cloud saves and leaderboards.
- Make server checksum generation authoritative and reachable through a real server-controlled write path.
- Restore coverage to configured thresholds with meaningful tests.
- Replace or formally de-scope monetization/analytics/ad stubs.
- Fix stale audit documentation so future agents do not inherit false confidence.

## Additional Test-Reliability Findings from Parallel Review

- Local `npm run ci` does **not** run coverage even though GitHub Actions does; this creates a local/remote gate mismatch.
- Test setup globally suppresses broad warning/error classes, including storage, checksum/integrity, Firestore/offline, and React `act` messages; this may hide regressions.
- Some tests depend on implementation internals via `as any` and private method access, making future refactors noisy.
- Date-sensitive daily challenge tests use wall-clock dates rather than a fixed `vi.setSystemTime`, creating midnight/timezone brittleness.
- IndexedDB tests primarily exercise fallback behavior, leaving real IndexedDB branches under-covered.
